# PRD Quality Review — 內部 SMS 閘道（sms-platform）

## Overall verdict
這份 PRD 的驗收條件寫得紮實（幾乎每個 FR 都有可測的狀態碼、次數與錯誤碼），範圍取捨與限制（重啟丟佇列、不得承載驗證碼、不做 failover）誠實地寫在願景、非目標與 FR-28，假設也完整索引回扣。風險在於策略層：v1 只有 `mock` 與假對端、佇列重啟即丟，既不能上線承載真實流量，也沒有解決觸發本案的「驗證碼斷線 2 小時」事故，成功指標量到的是「準備度」與「測試全綠」，不是論點本身（行為一致、單點查證）是否成立；而最大的決策風險（自建對比現成方案，§8 Q2）仍未解，文件卻標為 `status: final`。補上幾個行為缺口（冪等、Webhook 順序／逾時、FR-22 與 `mock` 的矛盾）與少量術語整理後，可交付下游。

## Decision-readiness — adequate
取捨多半以決策形式寫出並說明放棄了什麼：願景明說「刻意不承諾高可用」，§5 與 FR-28 把「重啟丟佇列」列為已接受限制，FR-9 把不做 failover 變成可測條件，§8 Q2 也誠實標出「這是最大的決策風險」並給出負責人與期限（閘道團隊 tech lead、架構開工前）。這些都不是「平衡考量」式的含糊語氣。

弱點在於決定的狀態：Q2 的結論可能讓整份 PRD「轉為遷移與包裝規格，並重新檢視 FR 範圍」，卻同時標示 `status: final`；Q1「負責人待指定」，Q3 的 30 萬則／月與 TCO 尚未查證，而 FR-16 的上限與 Q8 的佇列上限都依賴它。唯一的 `[NOTE FOR PM]`（§6.2 後續階段無啟動條件）放對了位置，但 Q2 這種真正的張力沒有同樣的 callout。

### Findings
- **[high]** 最大決策風險未解，文件卻標為 final（frontmatter `status: final`、§8 Q2、Q1）— Q2 若選現成方案，FR 範圍整個重來；Q1「負責人待指定」使「向五個租戶說明 v1 沒有解決原始事故」沒有人負責，卻是「第一個租戶換接前」的前置。*Fix:* 將 Q2 結論列為 PRD 進入 final 或架構開工的明確閘門（在 §0 或 §6 加一個 `[NOTE FOR PM]`，寫明「Q2 未結前，架構與 Story 拆分僅可視為暫定」），並在 Q1 指定負責人與期限，或把 status 改為 draft／conditional。

## Substance over theater — adequate
沒有 persona theater（只有一位具名使用者小林，且確實推動 UJ-1 與 FR-27）；願景有具體背景（5 團隊、3 語言、重試與回呼不一致），不是可換進任何 PRD 的空話；沒有 innovation 區塊硬湊。NFR 方面，FR-1 的 p95 < 200 ms、FR-17 的 `Retry-After` 正整數、FR-21 的 key 雜湊儲存都是產品專屬的界線，但容量與可靠度相關 NFR 偏少。

### Findings
- **[medium]** 容量與時限類 NFR 全數延後或缺席（FR-8、FR-12、FR-16、§8 Q8）— 重試間隔、Webhook 逾時、Webhook 重試排程、限流視窗型態、預設上限、峰值吞吐都沒有數字；唯一的量級線索（約 30 萬則／月，約每秒 0.1 則平均）反而說明容量並非難點，但 PRD 沒有據此給一個 v1 的容量上界。*Fix:* 至少為 Webhook 呼叫逾時、通知重試總時間、佇列上限量級寫出 `[ASSUMPTION]` 數值；明確說明哪些延後到架構階段是刻意的。

## Strategic coherence — adequate
論點清楚：把重試與狀態回呼收斂到單一閘道，讓行為一致、可在一處查證（§1 最後兩段），UJ-1、SM-1、SM-2 與之呼應，FR-27 是審查後補上的、直接支撐 SM-2 的一塊好補丁。反指標 SM-C1、SM-C2 也有指出會被誤最佳化的方向。

但 v1 的 MVP 屬「準備度」型：只有 `mock` 與假對端（§5「不與真實 Provider 帳號整合」）、佇列重啟即丟，SM-4 直接承認採用率目標移到「真實 Provider 接入之後」。換言之，v1 完成時論點並未被驗證，也沒有任何租戶能真的把流量放進來。

### Findings
- **[high]** v1 無法驗證自己的論點，且不處理觸發事故（§1、§5、SM-4、§8 Q1）— 論點是「集中重試與回呼後，行為一致、出事好查」，但 v1 沒有真實 Provider、重啟丟失全部訊息紀錄，SM-2 還被限定「僅限程序存活期間」；驗證碼事故明說「不會因 v1 而消失」。PRD 對此誠實，但沒有說清楚 v1 要證明什麼、證據是什麼。*Fix:* 在 §6 以一句話寫出 v1 的真正目的（例如「驗證介面、重試與回呼語意、租戶隔離，為接入真實 Provider 鋪路」），並把 §6.2 的啟動條件（Q5）轉成可決定的里程碑，否則 §6.2 的 `[NOTE FOR PM]` 所說「永久的臨時方案」風險就是現實。
- **[medium]** 成功指標多數量測「準備度」或「測試通過」，不是論點本身（SM-1、SM-3、SM-5）— SM-1 的基準是 §8 Q6 的差異清單，而該清單「目前沒有」，所以「行為一致」沒有可比較的起點；SM-3、SM-5 本質上是測試全綠，與 FR-20、FR-22 的驗收重複。SM-2 與 SM-4 較貼近論點，但 SM-2 沒有數字目標（例如排查時間）。*Fix:* 讓 Q6 成為 SM-1 的前置而不是並列待辦；SM-3、SM-5 降為完成門檻而非成功指標；為 SM-2 補一個可觀察量（例如「事故排查只需查閘道」的演練結果）。
- **[low]** 模板（4.5）與限流（4.6）與論點的連結未說明（§1）— 願景只談重試與回呼，模板與限流看起來像「有人想要的功能」。*Fix:* 在 4.5、4.6 的說明各加一句其與論點或事故的關係，或者標示為支援性功能。

## Done-ness clarity — strong
這是本 PRD 最強的一環：幾乎每個 FR 都有可驗收清單，包含精確的狀態碼、error code 與次數（FR-8「Provider 共被呼叫 4 次」、FR-9「`mock` Adapter 被呼叫 0 次」、FR-10 終態不可變且以「`failed` 後收到 `delivered`」測試證明、FR-15 message 列出缺少的變數名稱）。幾乎沒有「優雅處理」「合理效能」之類形容詞。

### Findings
- **[medium]** FR-22 要求以 `mock` Adapter 跑重試與簽章全路徑，但 `mock` 的失敗行為未定義（FR-22、FR-8、FR-24、詞彙表「假對端」）— FR-22 要求 FR-8 的跨模組測試「經 `mock` Adapter 走完整路徑」，但 FR-8 的驗收依賴「假對端連續回暫時失敗」，詞彙表又明說 `mock` 不經網路、與假對端不同。工程師無法判斷重試的 E2E 該用哪個。*Fix:* 擇一：規定 `mock` 可設定回應腳本（成功／暫時失敗／永久失敗），或將 FR-22 的路徑改為「`mock` 或假對端」。
- **[medium]** FR-28 對「終態訊息」的命運沒有交代（FR-28、§5、SM-2）— 本文說重啟丟失「佇列與記憶體內的訊息紀錄」，但驗收只測「重啟前尚未進入終態的訊息」回 404，終態訊息同樣在記憶體中，理應也是 404，且這會讓 FR-27 的失敗原因在重啟後一併消失。*Fix:* 驗收改為「重啟前建立的所有 `id`（含終態）回 404」，或明寫終態紀錄的保留行為並與 Q8 對齊。
- **[medium]** Webhook 通知的順序、逾時與重啟行為未定（FR-11、FR-12、UJ-1 高潮）— UJ-1 寫「先後收到 `sent` 與 `delivered`」，但 `sent` 通知若因租戶端暫時非 2xx 在重試，`delivered` 可能先到；FR-10 又允許對 `sending` 狀態的訊息直接回呼 `delivered`。通知重試在重啟後同樣丟失，PRD 沒說。*Fix:* 在 FR-11／FR-12 加一條：通知帶單調遞增的序號或時間，或明定「不保證順序，租戶以 `id` 加 `status` 處理」；寫明通知重試受 FR-28 限制。
- **[low]** 模板渲染後長度與 FR-1 的 70 字上限互動未定（FR-1、FR-14）— FR-1 對內容超長回 400，FR-14 在入佇列前渲染，但沒說渲染後超長要怎麼辦。*Fix:* 在 FR-14 加一條渲染後超長回 400 `invalid_request`（或 `invalid_template`）。

## Scope honesty — strong
非目標清單做了實際工作（§5 七條，每條有理由，並分清「政策約束」與「永久排除」）；`[ASSUMPTION]` 標註密集，且全部索引到 §9；§8 有 8 題，其中 Q2 有負責人與期限，是真正懸而未決的問題而非修辭問句。開放項目密度偏高（8 題待決、約 20 個行內假設、1 個 `[NOTE FOR PM]`），對「內部工具」是可接受的。

### Findings
- **[medium]** 重送與冪等性是被默默漏掉的缺口（FR-1、FR-28、§5）— FR-28 要求租戶自行處理「已收到 202 但訊息遺失」，實務做法就是重送；但 `POST /v1/messages` 沒有冪等鍵，重送在 Provider 已送出時會造成重複簡訊。這既不在需求，也不在非目標。*Fix:* 將「不提供冪等／去重」列入 §5 非目標並在租戶接入文件中警示，或新增冪等鍵 FR。
- **[low]** 開放項目數量與「final」狀態並存（§8、§9）— 約半數假設是「留給架構階段」的值，不阻擋；但 Q1、Q3、Q6、Q8 都沒有負責人或期限，只有 Q2 有。*Fix:* 在每題標註「阻擋什麼、由誰、何時」，其餘標為「不阻擋」。

## Downstream usability — adequate
詞彙表完整且要求逐字使用，FR 編號 1–29 連續、無重複，UJ 有具名主角，跨參照（Q7、Q8、FR-28、SM 對 FR）皆可解析。§0 主動說明 FR-27 至 FR-29 為審查後新增、編號不依閱讀順序，降低混淆。但整份只有一個 UJ，且部分 FR 的位置與主題不符，對 UX 與 Story 拆分的來源抽取略有干擾。

### Findings
- **[low]** FR-29（法遵：發送紀錄不外送）被放進 4.9「錯誤格式」（§4.9、§0）— 主題不符，Story 拆分時容易被誤歸到錯誤處理 Epic；且 FR-29 的 JTBD 與 §5 的 CPaaS 排除原因分散在三處。*Fix:* 移到獨立小節「合規與資料邊界」，或併入 4.2。
- **[low]** 跨功能 NFR 沒有編號（§4.9 「跨功能 NFR（本 PRD 規定的少數項目）」）— 內部 500 `internal_error` 不洩漏堆疊、日誌不記錄內容與 API key 兩條 NFR 無 ID，無法被 Story 或測試引用，且不在 FR-22 的測試範圍內。*Fix:* 編為 FR 或 NFR-1、NFR-2，並給驗收。
- **[low]** 術語漂移（§3、§8、addendum）— 詞彙表聲明「不另用供應商」，但 addendum 仍用「供應商」「供應商回呼端點」；正文「狀態」與「Status」混用；「發送紀錄」（FR-29）、「接入」「換接」「遷移」並用；「接入檢核表」「租戶接入文件」未在詞彙表定義；§6.2 稱「Open Questions」而章節為「待決問題」。*Fix:* 統一為詞彙表用語，並補「接入檢核表」定義。

## Shape fit — strong
內部工具、五個租戶、單一維運角色：以功能 FR 為主、一個旅程貫穿 API 與 Webhook、SM 偏營運導向，形狀合適，未過度形式化。唯一的取捨是 JTBD 列了法遵與維運者，但沒有對應 UJ，對此規模可接受（維運者行為由 FR-5、FR-21 涵蓋，法遵由 FR-29 涵蓋）。4.8（E2E 門檻）自述為流程性需求而非產品行為，放在 FR 列表內略顯突兀，但已誠實標示。

## Mechanical notes
- **ID 連續性：** FR-1 至 FR-29 連續且唯一；FR-27、FR-28、FR-29 依序插入 4.1、4.3、4.9 而非依序排列，§0 已說明。SM-1 至 SM-5、SM-C1、SM-C2 連續。UJ 僅 UJ-1。
- **交叉參照：** §2.1、§2.2、§5、§6.2、SM-1、SM-4、FR-28 對 §8 Q 編號的參照均可解析；FR-22 僅列 FR-1、7、8、10、11、12 為跨模組 E2E，未含 FR-27、FR-28。FR-22 說「4.1 至 4.7」，與 §6.1「八項功能」計法不同（4.8 本身是測試門檻）。
- **假設索引往返：** §9 的 13 條與行內 `[ASSUMPTION]` 逐一對上（FR-1、3、6、8、11、12、16、19、21、23、28、29、§4.9 NFR），無遺漏或多餘；FR-16 的「全域預設值」與「計數單位」兩條合併為一行，可接受。
- **UJ 主角：** UJ-1 有名有姓（小林）並內嵌背景，合格。
- **術語：** 見 Downstream usability 的術語漂移一則。
- **必要章節：** 願景、使用者、功能、非目標、MVP 範圍、成功指標、待決問題、假設索引俱全；缺少獨立的 NFR 章節（相關內容分散在 FR 與 §4.9）。
