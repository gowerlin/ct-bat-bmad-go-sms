# Product Brief: 內部 SMS 閘道（sms-platform）

## Executive Summary

sms-platform 是公司內部的 SMS 閘道，提供統一的 API 與 webhook 回呼。上游仍使用國內第三方簡訊供應商，我們不自己當供應商。

目前 5 個團隊、3 種語言（Go／Java／Node），各自串接 2 家供應商，每月約 30 萬則。重試與狀態回呼各寫一套，行為不一致，出事時要逐團隊追查。v1 把這兩件事收斂到一處，讓所有團隊行為一致、問題可在單一地方查證。

這份 brief 是 PRD 的輸入，也是五個團隊對齊範圍的依據。v1 刻意不承諾高可用，也不承載關鍵簡訊，詳見「Scope」與「Open Questions」。

## The Problem

- 5 個團隊各自實作重試與回呼，邏輯不一致。同一則簡訊在不同團隊可能重試次數、失敗判定、狀態通知都不同。
- 出事時沒有單一查證點，得逐團隊、逐供應商追查。
- 國外 CPaaS 與「發送紀錄外送」被法遵排除，不能用現成雲端方案。
- 共用 SDK 無法解決：重試與回呼需要集中執行，SDK 只能統一程式碼，不能統一執行行為。

## The Solution

一個純後端的內部閘道，各團隊只透過 API 與 webhook 接入：

- **統一送信 API**：訊息入佇列，由閘道負責送出。同一供應商失敗時重試 3 次，仍失敗則標記 `failed`。
- **統一狀態回呼**：以簽章 webhook 通知呼叫端，各團隊拿到的狀態語意一致。
- **模板與變數**，並對每個 API key 限流。
- **多租戶 API key**：租戶之間互相不可見。
- **Provider 抽象**：切換供應商靠設定，不改呼叫端。

## What Makes This Different

沒有技術護城河，價值在於「集中」與「合規」：

- 相對共用 SDK：能集中執行重試與回呼，而不只是統一程式碼。
- 相對國外 CPaaS：符合法遵（資料不外送）。
- 自建的代價：閘道成為新的單點，且需要持續維運。「自建優於採購」目前仍是假設，不是結論（見 Open Questions 第 2 題）。

## Who This Serves

**主要使用者**：各服務團隊的後端工程師。他們只透過 API 與 webhook 接入，不需要任何畫面。他們要的是：換接之後不必再自己寫重試與回呼，行為可預期，出事時能在一個地方查到原因。

**次要受益者**：負責事故排查與維運的人員，以及要求資料不外送的法遵單位。

## Success Criteria

- 每個換接的團隊，重試與狀態回呼的行為一致（同樣的重試次數、同樣的狀態語意）。
- 出事時只需查閘道一處，不必逐團隊追查。
- 每個功能上線都有自動化的端對端測試。
- 租戶隔離可被驗證：A 租戶看不到 B 租戶的訊息與狀態。
- 採用率：5 個團隊在兩季內全部改走閘道。

## Scope

**v1 範圍內**
- 只做後端 API，不做 Web 主控台（純範圍取捨，不是永久排除）。
- 單一程序、in-process 佇列，佇列介面抽象化，之後可換成 Redis。
- Provider 介面：mock，加上一個國內供應商風格的 adapter。adapter 只打假對端，不綁真實帳號。
- 重試、簽章 webhook、模板與變數、每 key 限流、多租戶 API key、設定切換 Provider。

**v1 明確不做**
- **不承諾 99.9% 可用性**：重啟會丟失佇列，也無法多副本。
- **不得承載驗證碼類關鍵簡訊**。
- 跨供應商自動 failover。
- 與真實供應商帳號的整合。

## Vision

v1 之後的目標是 99.9%：持久化佇列、多副本、監控，並加上跨供應商 failover。屆時閘道才有資格承載關鍵簡訊，各團隊也沒有理由退回直連。

## Open Questions

這些是尚未解決的問題，而不是已有答案的決定：

1. **v1 沒有解決原始事故**：驗證碼斷線 2 小時的事故不會因 v1 而消失，v1 只解決重試與回呼不一致。要如何向五個團隊說明這一點？
2. **自建對比現成方案**：開源閘道未評估，具 failover 的國內聚合商或國內服務也未排除。
3. **數字未查證**：自建的 TCO 與「約 30 萬則／月」都沒有查證過。
4. **遷移順序與起算點**：目標是兩季內全部換接，但「兩季」從何時起算、先接哪個團隊，目前沒有定義。
5. **後續階段何時做**：持久化佇列與多副本要在什麼條件下啟動，才不會讓 v1 變成永久的臨時方案。
