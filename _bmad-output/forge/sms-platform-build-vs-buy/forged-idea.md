# Forged idea：內部 SMS 閘道（sms-platform）

**定位**：公司內部閘道，統一 API；上游仍用國內第三方供應商，自己不當供應商。

**為什麼自建**：5 團隊、3 語言（Go/Java/Node）、各串 2 家供應商、約 30 萬則/月；重試與回呼各寫一套，出事難查。國外 CPaaS 與發送紀錄外送被法遵排除；共用 SDK 做不到集中重試/回呼。

## v1 鎖定
- 只做後端 API；不做 Web 主控台（純範圍取捨）。
- 單一程序、in-process 佇列，佇列介面抽象（之後換 Redis）。
- Provider 介面：mock + 一個國內供應商風格 adapter（只打假對端，不綁真實帳號）。
- 訊息入佇列，同一供應商重試 3 次，仍失敗標 `failed`；狀態以簽章 webhook 回呼。
- 模板＋變數；每 API key 限流；多租戶 API key，租戶互相不可見。
- 切換 Provider 靠設定。

## 已知限制（寫明）
- v1 **不承諾 99.9%**，**不得承載驗證碼類關鍵簡訊**（重啟會丟佇列、無法多副本）。
- 跨供應商自動 failover 不在 v1。

## 之後才算數
- 99.9% 目標（持久化佇列＋多副本＋監控）；閘道是新單點，各團隊不退回直連。

## 未解弱點
- v1 只解「重試/回呼不一致」，未解原始事故（驗證碼斷線 2 小時）。
- 開源閘道未評估；國內聚合商/具 failover 的國內服務未排除。
- 自建 TCO 與 30 萬/月數字未查證。
