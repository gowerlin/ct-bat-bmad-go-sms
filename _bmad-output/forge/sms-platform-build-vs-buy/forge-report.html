Forge Report：內部 SMS 閘道

2026-10-22 · 目標：檢驗想法是否成立 · 結果：HARDENED（附未解弱點）

結論

公司內部閘道，統一 API，上游沿用國內第三方供應商，自己不當供應商。5 個團隊、3 種語言、約 30 萬則/月，各自重試與回呼行為不一，出事難查。範圍收斂成一個「不承諾可用性、不承載驗證碼」的 v1。

鎖定的決定

  • 只做後端 API，不做 Web 主控台（純範圍取捨，與單點風險無關）。
  • 單一程序、in-process 佇列，介面抽象，之後換 Redis。
  • Provider 介面：mock + 一個國內供應商風格 adapter（只打假對端）。
  • 同一供應商重試 3 次，失敗標 failed；簽章 webhook 回呼狀態。
  • 模板＋變數、每 API key 限流、多租戶 API key 且租戶互相不可見。
  • 99.9% 目標：持久化佇列＋多副本＋監控之後才算數；v1 不承諾、不承載驗證碼。

被否決的選項與原因

  • 共用 SDK：三種語言，且重試/回呼須集中才查得到。
  • 國外 CPaaS：手機號碼為個資，法遵要求發送紀錄留在公司內；已與兩家國內供應商簽約。
  • v1 就承諾 99.9%：與 in-process 佇列矛盾（重啟丟訊息、無法多副本）。
  • v1 跨供應商自動切換：延後，記為已知限制。

存活下來的弱點

  • v1 排除驗證碼與自動 failover，因此沒有解決原始事故（驗證碼斷線 2 小時），只解「重試/回呼不一致」。
  • 開源閘道未評估；國內聚合商或具 failover 的國內服務未排除。
  • 自建 TCO 與 30 萬/月的數字未查證。
